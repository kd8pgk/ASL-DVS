Part 1 · Setting up the node

Node 1921 in rpt.conf

Transmit needs its own node in Asterisk. Node Talker writes it into rpt.conf, and then links it to the main node so its audio reaches the main node's transmitter.

1.1The block it writes

The setup adds a comment and a node block for node 1921. The block uses a USRP channel that listens on 127.0.0.1:34018 and sends to 127.0.0.1:32018. It is set to half duplex, with no hang time, no alternate hang time, no telemetry, and no unkey count, and it sets an identification recording on a timer. The block inherits the templates of the main node, so it shares that node's settings.

The setup also adds node 1921 to the main node's [nodes] line, so that Asterisk will link to it.

1.2Taking over from Node Recorder

If node 1921 already exists as a Node Recorder block, the setup takes it over, so that recording continues from this node. If a node 1921 exists that Node Talker did not write, the setup refuses and asks the operator to remove it or pick another.

1.3Asterisk restart

After the file is written, Asterisk must be restarted before the node takes effect. A backup of rpt.conf is kept with each change.

1.4Readiness

The transmit path is ready when the node 1921 block exists with the right channel, the main node is set, and the [nodes] line includes node 1921. The page shows the state from this check, and the link is reported as linked or not linked from the main node's current links.

Part 2 · Keeping it linked

The link keeper

A background loop checks every 20 seconds. If the transmit path is ready and node 1921 is not linked to the main node, the loop links it and writes a log line. The loop logs the first failure, and logs again when the link comes back. When the link is up, the loop does nothing.

Unlinking happens only when the transmit path is turned off or Node Talker stops. Ending a transmission does not unlink the node.

Part 3 · Key-up

Checks before the node keys

When the page asks to key, the server runs these checks in order:

  1. Ready. The transmit path must be ready (Part 1.4). If not, the key is refused as "not-ready".
  2. Linked. Node 1921 must be linked to the main node. If not, the key is refused as "not-linked".
  3. Busy. With busy_lockout on, a key is refused as "busy" while the channel is active (Part 2 of the RX series), unless Node Talker itself unkeyed less than one second ago. This stops a key-up over someone else's transmission.
  4. In use. Only one operator can hold the key. A second operator is refused as "in-use".

A refused key gives the operator a short message, for example "The node is busy (someone is talking)."

When the key succeeds, the buffers are cleared and a new session starts. If phone tones are on (Part 6), the phone is opened as well.

Part 4 · Audio in

From the page into the buffer

  1. The page sends microphone audio as binary WebSocket messages. Each message is 16-bit PCM.
  2. The server accepts audio only from the operator who holds the key. Audio from anyone else is ignored.
  3. The server cuts the audio into 320-byte frames (20 ms). Each frame gets the transmit gain (tx_gain_db, when the level settings are active) and its peak level is noted.
  4. Frames wait in a queue. The queue holds up to 50 frames (1 s) for a normal transmission, or 300 frames (6 s) for a phone session.

If the queue passes its limit, the oldest frames are dropped.

Part 5 · The pacer

Sending at a steady pace

A paced loop runs every 20 ms and decides what to send for that tick. The key rules are:

StageWhat happens
StartNothing is sent until the queue holds the transmit buffer (tx_buffer_ms, default 120 ms, or six frames). If the buffer never fills, sending starts once the fill time has passed.
SendingOne frame is sent for each tick. A fade-in is applied after a gap.
GapIf the queue runs dry while sending, the pacer fades out the last frame and counts a gap. It then waits for the buffer to refill before it sends again.
ReleaseWhen the operator lets go, the pacer sends what is left, fades the last frame out, and then stops.
Time limitAfter tot_sec (default 120 s, from 30 to 600), the transmission ends with the reason "timeout".
DeadmanIf no audio arrives for one second, the transmission ends with the reason "deadman".

The gap count is part of the transmission state and the log. A transmission with gaps is logged as a warning.

Part 6 · Out to Asterisk

USRP packets

6.1The packets

Each frame goes to Asterisk as one UDP packet. The packet starts with a 32-byte USRP header, followed by the 320 bytes of audio. The header carries a sequence number that rises with each packet, and a key bit. The key bit is set on the packets that carry audio, and is cleared on the packets that end the transmission.

6.2Ending a transmission

When the transmission ends, three silent packets are sent with the key bit cleared. Asterisk then drops its transmitter.

6.3The drain loop

The transmit node also sends its own output to 127.0.0.1:34018, and a drain loop listens there. The loop forwards every datagram to the Node Recorder's forwarding port, which is how this channel's audio reaches Node Recorder. If the port cannot be opened, the loop logs a warning and tries again every 60 seconds.

Part 7 · Phone tones

The phone session

When phone tones are on (phone_tones, on by default), a key-up also opens a phone session on the node. The page's codes are sent as tones: *99 to open and # to close by default. The phone session holds the transmission for up to 5 seconds, and keeps it open for a lead time (phone_lead_ms, default 500 ms) after the close code. Phone sessions use a larger queue, so a phone can keep speaking on a slow link.

The phone path uses the phone's own call protocol (SIP, IAX2, or a similar type), and was not traced in full for this summary.

Part 8 · Points for the book

What the TX path shows

8.1Two checks stop a bad key

The link check and the busy check stop most bad transmissions before the node keys. The busy check is the one operators need to understand: a refused key on a busy channel is the system doing its job, not a fault.

8.2Ending is always clean

Every ending, whether release, timeout, deadman or a dropped connection, sends the same silent packets and writes a log line with its reason.
