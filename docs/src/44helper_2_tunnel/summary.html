How a Tunnel Is Set Up

44helper builds a WireGuard tunnel to the 44Net Connect service, so the node can reach 44Net. This summary covers the configuration it accepts, the numbered steps the tabs run, the routing it installs, the boot order, the test-then-keep modes, and the router option.

Part 1 · The modes

Which tunnel for what

The same WireGuard tunnel (interface wg0) can be set up in five ways. They differ in what goes through the tunnel and in how much can be tested before it is kept.

Part 2 · The configuration

What a config must contain, and what the helper changes

2.1What is accepted

The config is pasted in, copied from the 44Net Connect portal. The helper rejects it unless it has these sections and fields: an [Interface] section, a [Peer] section, a PrivateKey, a PublicKey and an Endpoint. A PrivateKey that is a placeholder, or that does not look like a WireGuard key, is refused with advice to copy the real key from the portal. A paste with no Endpoint is treated as a partial paste.

2.2What is changed on the way in

The helper normalises the config before writing it. It reports each change:

ChangeWhen
SaveConfig = true is removedAlways, because wg-quick would rewrite wg0.conf on every stop and drop 44helper's settings.
Address changed to a /32When the address is a subnet. A 44Net Connect tunnel is one address. The operator can untick this when ARDC gave a subnet.
PersistentKeepalive = 25 addedWhen it is missing or off. Without it, a quiet tunnel goes idle and 44Net stations cannot reach the node.
AllowedIPs fitted to the tabA config for the wrong tab (full on Split, split on Full) is blocked. The operator can choose to rewrite its AllowedIPs, or paste it on the right tab.
DNS line removedWhen systemd-resolved is not answering, or there is no resolvconf command, or the DNS server is not inside the tunnel's AllowedIPs. DNS is then set from the DNS card.
Split routing block and endpoint pinAdded for a split tunnel (Part 3, step 4b), and to keep the tunnel server's own route outside wg0.

2.3Where it is written

  • The live file is /etc/wireguard/wg0.conf, written with mode 600 by a safe replace. The private key is never written to the log.
  • If a previous config existed, it is saved as wg0.conf.pre-replace. The DNS and MTU settings from the old file are carried over into the new one.
  • A copy is kept in the library folder, so the config can be restored later.
  • The tunnel's settings are saved in 44helper's config as the mode (pi), the interface (wg0), the path, and the kind (full or split).
Part 3 · The numbered steps

Full and Split tabs, steps 1 to 6

The page shows the steps in order. Each step has a command, and some have a verify check. Steps run through the same install engine described in Stage 1, with the same field and gate rules.

StepTitleWhat it runs
1Firewall prerequisiteInstalls firewalld and enables it.
1asystemd-resolved prerequisiteInstalls wireguard-tools and systemd-resolved, and enables resolved (ARDC guide, section 1a.1).
2Create the 44NetConnect firewall zoneCreates the zone permanently and reloads firewalld.
3Add inbound services and portsA checklist. IAX2 uses the bind port from the config (4569/udp by default). EchoLink uses 5198 to 5199/udp and 5200/tcp.
4Paste the WireGuard configThe config is pasted and written (Part 2).
5Attach wg0 to the zoneAdds the interface wg0 to the 44NetConnect zone, then reloads firewalld.
6Enable and start the tunnelEnables and starts wg-quick@wg0, waits for the handshake, then runs the boot order (step 6b).

Sub-steps: 4a is DNS and MTU, 4b is split routing (Split tab), or outbound reflector ports on the Full tab, and 6b is the boot order.

3.1Step 1 and 1a: why the prerequisites

The tunnel is managed by firewalld, and the DNS settings need systemd-resolved, so both are installed first. Step 1a installs wireguard-tools, which provides wg-quick.

3.2Step 2 and 5: the firewall zone

Traffic that arrives over the tunnel is governed by the 44NetConnect zone. Its interface is wg0 (step 5), and the services and ports the operator needs are listed in it (step 3). The zone holds the tunnel's inbound rules that the helper manages.

3.3Step 6: the handshake and the fallback unit

  • If the system has the standard wg-quick template, the step enables and starts wg-quick@wg0, restarting it if it is already active. Otherwise it writes a fallback unit, 44net-tunnel.service, that runs wg-quick up /etc/wireguard/wg0.conf.
  • A full tunnel (AllowedIPs 0.0.0.0/0) needs nftables or iptables-restore for wg-quick's routing rules. If neither is installed, the step stops and asks for nftables to be installed first.
  • After the start, the helper waits up to 15 seconds for a handshake with the 44Net server. If there is none, it warns to check the endpoint and the portal approval.
  • Then it keeps the tunnel server's own address on the normal route, so its packets do not loop into wg0 (the endpoint pin).

3.4Step 4a: DNS and MTU

DNS modeWhat it sets
OffNo DNS handling by the tunnel.
resolvectl, fullSets 1.1.1.1 and 9.9.9.9 as the tunnel's DNS servers through resolved.
resolvectl, splitSets 44.0.0.1 as the tunnel's DNS server, for 44Net names.
DNS lineWrites a DNS = line into the config: 1.1.1.1, 9.9.9.9 and 44.0.0.1. Needs the resolvconf command.

The MTU can be set between 1280 and 1500. Blank or "off" removes it. Both settings are kept in marked blocks in the config, so they survive a re-paste.

3.5Step 4b, split: routing with a table and a mark

For a split tunnel, the helper adds a routing block to the [Interface] section. The block is marked, and it contains:

  • Table = 4445 and FwMark = 0x4445. The 44Net routes live in table 4445, not in the main table.
  • A PostUp rule that sends traffic not carrying the mark to table 4445, and a PostDown rule that removes it.

WireGuard's own packets carry the mark, so they always take the normal route, on whichever adapter is up. The helper restarts the tunnel and then waits up to 30 seconds for a handshake. A config that already has its own Table or FwMark lines is refused, rather than changed.

3.6Step 4b, full: outbound reflector ports

On the Full tab, a card named Outbound reflector ports (egress) adds and removes reflector ports through separate actions. The card's exact effect on the routes was not traced for this summary.

3.7Step 6b: the boot order

The boot order makes the tunnel come back after a reboot, and makes DVSwitch wait for it:

  • A boot script, /usr/local/sbin/44helper-netready, runs as 44helper-netready.service. It waits up to 180 seconds at boot for the default route and, when the tunnel is configured, for wg0 and its handshake. A later pass (the late check) waits up to 1,200 seconds.
  • A time wait of 90 seconds (44helper-timewait) gives the clock time to sync, because a Pi's clock can start behind after a power cut and the tunnel server then ignores its handshakes.
  • A drop-in is added to wg-quick's unit and to the DVSwitch restart units, so they start after the network check. The boot log is kept at /var/lib/44helper/boot.log.
  • When the tunnel is enabled, the boot order is applied with it. Any DVSwitch services that were enabled but stopped are started.

3.8Locks between tabs

A Full and a Split config cannot both be in use, so each tab is locked when the other kind is installed. The locked tab shows a banner and an "Acknowledge and unlock" button, so a working tunnel is not overwritten by accident.

Part 4 · Half tunnel

Only ASL and EchoLink through the tunnel

The half tunnel sends the node's ASL and EchoLink traffic through the tunnel, and leaves everything else on the normal route. It is built as a test first: nothing is kept until the operator chooses so, and an automatic undo runs if they do nothing.

4.1Before the test: Check first

Check first reads the current state: the tunnel, its address, its endpoint, the firewall zone of wg0, and the routing. It lists anything that blocks the test. The last good Check is valid for 30 minutes. Arming the test refuses when there has been no good Check, or when it is older than that.

4.2Arm the auto-undo

Arming starts a 15-minute timer (44helper-halfundo). When it fires, the undo script puts everything back. The test state is kept in /run/44helper-half, which is cleared at reboot. Arming refuses while the full-tunnel-with-exceptions test is on, so the two tests cannot overlap.

4.3The five test steps

StepWhat it does
2. Restart tunnel in half modeWrites a temporary copy of wg0.conf under /run, and restarts the tunnel with it. The half tunnel needs the full 0.0.0.0/0 range, as the helper's own note says. The permanent config is not changed.
3. Add tunnel route tableAdds a routing table (4444) with the 44Net networks (44.0.0.0/9 and 44.128.0.0/10) and routes through wg0. The tunnel server's own address stays on the normal route.
4. Send ASL and EchoLink into the tunnelAdds policy-routing rules, at fixed priorities, so that the ASL and EchoLink traffic uses table 4444 and the rest uses the main table.
5. Open tunnel portsAdds the ports the test needs to wg0's zone (the EchoLink range 5198 to 5199/udp is among them), and records which were added.
6. Loosen the return-path check on wg0Changes the reverse-path filter for wg0, because replies can arrive on an interface the filter does not expect. The original value is saved so it can be put back.

Each step must be done in order: step 3 cannot run before step 2, and so on. Every step records what it changed, so that the undo can reverse it.

4.4Keep, undo, or make permanent

  • Keep cancels the auto-undo timer. The test stays until the operator chooses Undo now or the node reboots.
  • Undo now reverses the steps.
  • Make permanent needs checks less than 15 minutes old. It writes the half-tunnel settings to /etc/44helper/halftunnel.json, a sysctl file for the loosened filter (/etc/sysctl.d/90-44helper-halftunnel.conf), a login reminder script (/etc/profile.d/44helper-halftunnel.sh), and a removal script with a copy of the old config. The removal script can be run later to take the half tunnel out.
  • Remove permanent runs the removal, with the same care as the undo.
Part 5 · Full tunnel with exceptions

Full tunnel, with some traffic kept off it

A full tunnel carries all internet traffic. The exceptions wizard lets the operator keep chosen LAN addresses, hosts and ports on the normal route, while the rest goes through the tunnel. Like the half tunnel, it is tested with an automatic undo first.

5.1The steps

StepWhat it does
Check firstReads the state before the test, as for the half tunnel.
ArmStarts the auto-undo timer (44helper-fullxundo) and the test state in /run/44helper-fullx.
2. Keep replies from the LAN address on the LAN linkAdds a rule that keeps replies to LAN addresses on the local link, so that LAN clients still reach the node.
3. Send the bypass list around the tunnelAdds the hosts and ports the operator chose to the normal route, at fixed priorities.
Keep, undo, make permanentAs for the half tunnel. Permanent settings are saved in /etc/44helper/fullx.json.

The exceptions are kept in blocks with the helper's own markers, so they can be found and removed cleanly.

Part 6 · Router

The router option

For an OpenWrt-based router, such as a GL.iNet, the tunnel can run on the router instead of the Pi. The Router Install tab walks through it as ten numbered steps. Each step checks the router before it changes anything.

StepTitle
1Router access
2Router firmware and model detection (2a: LuCI status for GL.iNet and OpenWrt)
3Allocation type
4Capture the WireGuard config and the LAN subnet
5Apply the WireGuard config to the router (uci)
6Set the router's LAN IP to the subnet (where the model needs it)
7Bring up the tunnel
8The Pi's address (its LAN address for model B, its 44Net address otherwise)
9Port forwards, and the WireGuard firewall zone fix
10Verify (a ping and a traceroute to 44Net)

The router path has its own actions for installing the LuCI page, binding an address to the Pi, adding static bindings, and adding port forwards. Verify is the step that records the router tunnel as working. Router settings are kept in 44helper's own config, in the tunnels section, under the router keys (tunnel.router.*), not in wg0.conf.

Part 7 · Points for the book

What the tunnel code shows

7.1Every mode has a way back

The half tunnel and the exceptions wizard are both tested first, with a timer that puts the node back. Make permanent writes a removal script next to the settings, so the change can be reversed later. The book can describe this as a design that never leaves the node without a way back, while noting that a restart of the tunnel can drop a remote session (see the watchdog summary).

7.2The config is the source of truth

Most settings (DNS, MTU, endpoint pin, split routing) are written into wg0.conf as marked blocks. A re-paste carries them over. This keeps the tunnel's state in one file.

7.3The tests are mutually exclusive

Each test's arm action refuses to start while the other test is on, and the exceptions arm also refuses when the tunnel is already permanent. A node can run one test, or one permanent mode, at a time.

7.4Not checked

  • The exact routing rules that wg-quick adds for a full tunnel, which come from the wg-quick template, not from 44helper.
  • The router steps' commands, which were read by title and route, not in full.
  • The live effect of the reverse-path change in the half tunnel's step 6.
  • The 44Net server's side of the handshake and the portal approval.
