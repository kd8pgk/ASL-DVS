Part 1 · There is no single switch

The rule is set feature by feature

The tools do not share one LAN gate. Each feature decides for itself whether a request must be local, and each uses its own test. The servers listen on every interface, so the rule is applied in code, not by a firewall that the tools configure.

  • Listening. The Dashboard and wifimon bind to 0.0.0.0, so they accept connections on every interface, including the WAN side when the node has one.
  • Gating. A feature that must be local checks the request's source address before it does its work.
  • Labelling. Some views only report whether a client looks local. They do not refuse anything.

Read the book's wording with that split in mind. "LAN only" is true of a named feature, not of a whole tool.

Part 2 · What counts as local

The address test

2.1The standard test

Most tools parse the peer address with Python's ipaddress module and accept it when it is one of:

  • is_loopback: the node itself (127.0.0.0/8, ::1)
  • is_private: the RFC 1918 ranges and the IPv6 unique-local range
  • is_link_local: the self-assigned 169.254.0.0/16 and fe80::/10 ranges

IPv4-mapped IPv6 addresses (::ffff:a.b.c.d) are unwrapped first, so a mapped LAN address is treated like its IPv4 form.

2.2Tailscale is added in two places

Node Talker, Node Recorder and amp Node Talker (_TAILNET) and the SysMon Node Listen view (_NL_TAILNET) also accept 100.64.0.0/10. That range is the carrier-grade NAT block that Tailscale uses, so a device on the node's tailnet counts as local there. The standard test in the other tools does not accept it, because Python does not count that block as private. pibrary only names it in its access label ("Tailscale or another VPN").

The address test is not the same as a logged-in user. A tailnet device that reaches a gated feature still needs the feature's own checks, such as a login, where those apply.

2.3What a proxy does to the test

A request that arrives through a proxy or a tunnel comes from the proxy's address, which is often local. The tools therefore check for proxy headers as well (see the Security hardening summary, Part 5). The rule differs by tool. wifimon and the 44helper terminal refuse any request that has one of their listed headers, whatever its address. Node Talker and Node Recorder treat a request as outside only when it comes from a loopback address and has one of their headers, which is the shape of a tunnel program running on the node. A LAN device that adds such a header to its own request is still treated as local there.

Part 3 · The rules that are enforced

Where a request is refused

3.1wifimon control actions

The control gate (_control_gate) runs before any change. It checks, in order:

  1. The session is logged in (401 otherwise).
  2. The source is loopback or private, and is not the unspecified address. The request has no proxy header (403, "Changes only work from this machine or the local network, not through a proxy.").
  3. Changes are switched on by the file /etc/wifimon/install.enable (wifimon's config folder). The file must be a regular file (a link does not count), owned by root, and not writable by group or others. Otherwise the answer is 403.

The gate covers only the control paths: radio, device disconnect, switch, mode, forget, service restart and install start. Other paths are not gated by the LAN test.

3.244helper terminal

The terminal check (_term_client_ok) refuses any request with a proxy or Cloudflare header. It accepts only loopback, link-local and private addresses, and refuses the rest with the message "The terminal only works from your LAN." Enabling the terminal (_term_can_enable) also needs root and the terminal-enable switch.

3.3Node Talker and Node Recorder outside access

Both tools treat a peer as outside (WAN) when the request is proxied (Part 2.3) or its address is not local. Every GET and every POST starts with this check. An outside request is refused with 403, "Node Talker is not open to the internet (allow_wan is off)," unless the allow_wan setting is on. The default is off, so neither tool is open to the internet until an operator turns it on. The check covers the page, the audio stream and the WebSocket, since all of them begin as a GET.

When allow_wan is on, logins from outside have their own cap: after 20 failed internet logins in 10 minutes, every internet login waits until the window ends.

Node Recorder also has a route that answers only a loopback peer that is not proxied: the recording status (403, "The recording status is for programs on this Pi only").

3.4The Dashboard local API

The Dashboard's local API accepts only loopback peers, and it also needs the local key. This is the strictest rule in the set: the local API is not reachable from the LAN at all (see the security summary, Part 3).

Part 6 · Points for the book

What the LAN-only policy means in practice

6.1"Local" means the whole home network

A private address is any device on the LAN, not one trusted person. The policy keeps the internet out, but it does not separate household devices from each other. The book should say that plainly.

6.2The tunnel is the main exception

A tunnel that brings internet traffic onto the LAN, such as a Cloudflare tunnel, is refused by the proxy headers where those are checked (wifimon, the 44helper terminal, and Node Talker and Node Recorder for a tunnel program on the node itself). A tunnel that places the remote device on the LAN, such as Tailscale, is accepted by design. Operators who want the tunnel refused must rely on the feature's own login.

6.3The rule is set in code

Changing who is local means changing the code of each tool. There is no setting that moves every feature to a stricter policy at once.

6.4Not checked

  • Every route in the Dashboard, SysMon and instmon for a local test. Only the gates named above were read.
  • amp Node Talker's use of the outside test.
  • How the wifimon install-enable file is set on a running node.
  • Whether the firewall rules the tools open are restricted by source address.
