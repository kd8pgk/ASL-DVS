How SysMon Parses the System

Where SysMon gets its system information, how it reads the ini and conf files, how it builds the port list, and how it decides whether the Pi's firewall lets the node's traffic through.

Part 1 · Scope and method

What was read

SysMon gathers its data in one background loop, keeps the latest values in a shared state, and serves that state to the pages. Parsing happens at three points: when a value is read from the system, when a config file is read, and when a firewall or socket command's output is read.

1.1Method

  • Each parsing function was read in full, along with the functions it calls for its data.
  • The full build's copy of each named function was compared by code structure. All 31 match the Pi Zero 2 W build, so the behaviour described here applies to both.
  • Nothing was run on a node. Behaviour is described from the code.

1.2The main loop

StepHow oftenWhat it does

Quick tests and port conflictsEvery third pass (30 s)Each pinned service's state, its port, and its config file. Then the duplicate-port check.

The pages read the stored state. Requests that need a fresh answer (the Ports list, a probe, a firewall check) run their own command at the time of the request.

Part 2 · System information

Where each value comes from

Most values come from a file under /proc, /sys or /etc, or from a short command. Each reader returns an empty value on failure, and writes a debug line only. A missing value shows as a dash on the page, not as an error.

2.1What "unavailable" means

When a reader fails, it returns an empty value. For throttling, the page reads "vcgencmd unavailable" from an empty result, so a missing command and a healthy Pi look different. For the other readers, a failure looks like a blank. The book should say that a dash can mean either "not known" or "no data".

Part 3 · Ports

Listening ports

3.1Reading the socket table

The port list comes from ss -tlnpu. Each line is parsed like this:

  1. The header line is skipped.
  2. The protocol (first field) must be tcp or udp.
  3. The local address (fifth field) is split at its last colon. The port must be all digits, so the address and the port are kept apart correctly for IPv6 forms.
  4. The process ID comes from pid=, and the process name from the first quoted word after it.

The list shows each protocol and port once (the first entry wins), sorted by port number. A port bound on both IPv4 and IPv6 therefore appears once.

3.2Labels from the pinned services table

The labels in the port list come from the pinned services table. Each row has five fields: unit, description, config file, port and protocol. Rows that begin with __GROUP__: start a group. The default table names these groups: System, ASL-DVS, Asterisk Core and M17. The default table gives SSH port 22, Cockpit 9090, the Dashboard 8989, SysMon 9999, Asterisk 4569/udp, and Allmon3 8080.

A label is attached by port number only. If two units share a port, the later one in the table wins. A row whose port is -, parse or blank has no label.

3.3The parse value is not used

The table's port field accepts the word parse, which seems meant to read the port from the unit's config file. No code does this. The quick tests and the service list skip parse, and show it as a dash. A row written as parse therefore never gets a port. The book should not describe this as working.

3.4Duplicate ports

Every 30 seconds, a port is reported as a conflict when at least two different process IDs are listening on the same protocol and port. Two sockets from one process do not count.

3.5Quick tests

For each pinned unit, the quick test checks four things in order: the unit is installed, it is active, its port is listening, and its config file exists and is not empty. The result is pass, fail or not applicable.

Caution. The listening check is a substring test: it looks for the text :port anywhere in the ss output. Port 443 would therefore also match a listener on 4430. The duplicate and probe code uses a different, exact test (see 3.6), and the quick test should match its style.

3.6On-demand probes

The probe page tests one port over TCP, HTTP or UDP. It builds its target list from the addresses that ss reports for that port, then adds loopback (127.0.0.1 and ::1) as fallbacks. Addresses of 0.0.0.0 and * are replaced by loopback. A link-local IPv6 address keeps its interface scope. Nothing is probed beyond the node itself.

The phone check's UDP listener test (not the probe page) uses an exact suffix match on :port, so it does not match a longer port. This is the safer form.

Part 4 · Config and ini files

Reading the conf and ini files

4.1Which files are opened, and how

  • Asterisk conf files. A file is accepted only if its name matches ^[\w\-]+\.conf$ and holds no slash or ... It is read from /etc/asterisk.
  • Other ini files. These are opened by an explicit list of paths, tried in order. Examples: Analog_Bridge.ini in /opt or /etc; USRP2M17.ini in /opt/USRP2M17; DVSwitch.ini, MMDVM_Bridge.ini and the YSF, P25 and NXDN gateway ini files in /opt, /etc and /etc/dvswitch; allmon3.ini in the Allmon3 folder.
  • Size. Any file is read up to 64 KB. Beyond that, the text is cut and a line says so. A key near the end of a large file can be missed.
  • Decoding. Files are read with errors replaced, so a bad byte does not stop the read.

4.3How the section parser works

  • A section header is a line in square brackets. A key is name = value. In the rpt.conf parser a semicolon ends the value; in the Phone parser an escaped \; is kept and only an unescaped one starts a comment.
  • Key case differs by parser. The rpt.conf and Phone parsers lower-case keys. The DVSwitch and USRP2M17 parsers keep the original case. A search by key must match the parser's case.
  • The generic _ini_sections function takes the header and key patterns as parameters, so each file type can define its own rules.

4.4The Phone context loader

The phone checks read the Asterisk files as one set. _ph_parse_file follows #include and #tryinclude lines, up to three levels deep. Each file must be 1 MB or smaller, and its name must match ^[\w.\-]+$. Lines between ; >>> dvs-phone and ; <<< dvs-phone <<< are marked as managed by the dashboard, as are whole files named dvs_phone_*.

Part 5 · The firewall

Deciding whether the Pi lets traffic in

The firewall check does not read the whole firewall. It asks one question: are the UDP ports the node needs open to incoming traffic? The two ports it needs are the SIP port and the RTP audio range.

5.1Which firewall is found

OrderTestNote
1firewall-cmd --state says runningfirewalld
2ufw is installedInstalled is enough. Whether ufw is active is checked later.
3nft is installednftables
4iptables is installediptables
5None of the above"no firewall on the Pi"

5.2Reading the rules

  • firewalld. Each active zone is read with --list-all. If a zone's target is ACCEPT, everything is open. Otherwise, the zone's ports are read, its services are expanded from their XML files (in /etc/firewalld/services or /usr/lib/firewalld/services, following includes up to four levels), and its rich rules are matched for port, protocol and accept, reject or drop.
  • ufw. ufw status verbose is checked first. If ufw is not active, the check stops. If the default policy allows incoming traffic, everything is open. Otherwise ufw status numbered is read. IPv6 rules are skipped. ALLOW and LIMIT rules count.
  • nftables. The ruleset is read. If every input chain accepts everything, the result is "open". Otherwise the check says it cannot read the rules port by port.
  • iptables. The INPUT chain is read. If the policy accepts and there is no DROP or REJECT, the result is "open". Otherwise the check says it cannot read the rules port by port.

5.3The coverage check

Only UDP rules that allow traffic are collected. The needed range (one port for SIP, or the RTP range) is compared with them, and any part not covered is listed as a gap. The result is one of five states:

StateMeaning
openEvery port in the range is allowed.
partialSome ports are allowed. The gaps are listed.
closedNone of the range is allowed (the whole range is a gap).
nofilterThe firewall lets everything in (firewalld target ACCEPT, ufw default allow, or an accept-all chain), or ufw is not active.
unknownThe firewall's rules cannot be read port by port (nftables or iptables with filtering).

5.4Fix advice

The advice names the port by taking the last word of the check's label, then gives the command for the firewall found: a firewalld command, a ufw allow rule, an nftables reload, or a general instruction when none is found.

5.5What the check does not cover

  • Only UDP. The TCP ports in the pinned table (Dashboard, Cockpit, Allmon3, SSH) are not checked against the firewall.
  • IAX2 on 4569/udp is not checked, although it is a UDP port that the node uses. The coverage check has only two entries: SIP, and audio.
  • Only the phone checks call the coverage code. The Ports tab does not show firewall state beside each port.
Part 6 · Points for the book

What the parsing shows

6.1A rule's source is ignored

In the firewall check, a rule counts as "open" if it allows UDP, whatever its source. A firewalld rich rule that accepts UDP from one address, and a ufw rule that allows UDP from one subnet, are both counted as open to everyone. The source field is read, but never used. A node could therefore show a port as open when only a single address can reach it. Fix this before the book describes the check as a test of reachability.

6.2Substring port match in the quick test

The quick test finds a listener by searching for :port anywhere in the output. Port 443 would match 4430. The exact match used elsewhere (endswith) avoids this, and the quick test should use it too.

6.3The parse port is not implemented

The pinned table advertises a way to read a port from a config file, but the code never does it. A user who writes parse gets a dash and no test. The book should either describe the port table as manual, or the code should be finished.

6.4Failures are silent

A reader that fails returns an empty value and logs only at debug level. The page then shows a dash. A missing command, a permissions problem and a healthy empty value look the same. The book should tell the operator where to look (the debug log) when a value is always blank.

6.5Truncated files

A conf file over 64 KB is cut, and the parsers see only the first part. This is unlikely for the usual Asterisk files, but a large rpt.conf or a long dial plan would lose its tail without a warning on the page.

6.6Two ways to match a port

The quick test uses a substring match, and the phone check's UDP listener test uses an exact suffix match. The port list uses a third method: it parses the full socket table and keeps the first entry for each port. Pick one for the book, and note that the substring form can report a listener that is not there.

6.7Duplicate labels

Two pinned units on the same port give one label, the later one. A second unit on that port is not shown in the list, so an accidental clash may not be noticed until the duplicate check reports it.
