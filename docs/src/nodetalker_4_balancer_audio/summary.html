Part 2 · The level switch

Why some settings have no effect

Gain, the listen buffer and the transmit buffer are read through a single rule. When tune_enabled is off, the server uses the defaults for those three settings, whatever is saved. The saved values take effect only when the level switch is on.

SettingLevel switch offLevel switch on
rx_gain_db0 dBSaved value
tx_gain_db0 dBSaved value
tx_buffer_ms120 msSaved value
jitter_msPage uses 250 msSaved value

The filter, AGC, gate, notch, kerchunk and busy settings are read directly from the saved values, so they take effect whether or not the level switch is on.

When a balancer change turns the switch on, the other level settings are pinned to the values that were in effect while the switch was off. So the change is the only thing that is heard, not a jump to several saved values at once.

One thing overrides the level switch: a favorite. A favorite (a saved connection in the favorites list) can carry its own RX gain and TX gain, from -12 to +12 dB. While that favorite is the active connection, its gains replace the saved RX and TX gain, whether the level switch is on or off. When the favorite is disconnected, the override is cleared and the saved values apply again. The saved settings are not changed.

Part 3 · The balancer

How a balance run changes settings

The balancer runs in the page. It makes one change at a time, measures again, and keeps the change only if the score does not get worse. The server does not compute the changes; it saves and restores the settings.

3.1Starting and undoing

  1. Snapshot. The server saves the current balance settings (the level switch, RX and TX gain, RX filter and gate settings, the listen buffer and the transmit buffer) to a file, nodetalker_balance.json. If that file already exists, a new run is refused until the earlier one is restored or kept.
  2. Restore. Writes the saved settings back and removes the file.
  3. Keep. Removes the file and leaves the changed settings in place.

A test that is turned off under Tests (tests_off) cannot start a balance run.

3.2The tone rounds (RX gain)

The page runs the RX tone test (Part 4) and reads the processed level of each returned tone. The score is based on the 1000 Hz tone (or the loudest tone if 1000 Hz is missing), which should come back at -16 dBFS after the cleanup stage:

  • The difference from the target is measured. If it is within 1.5 dB, nothing changes for that tone.
  • Otherwise the RX gain moves by the difference, limited to 6 dB a round, and kept between -12 and +12 dB.
  • Dropouts count against the score at half weight. If tones drop out, the listen buffer moves up through 150, 250, 500 and 1000 ms, instead of the gain.
  • The run makes up to three rounds. If a round scores worse than the one before by more than 0.5, that change is undone and the run stops.

3.3The live rounds

During a live check, the balancer measures the operator's audio on both sides:

  • Receive score: three times the clipping percentage, twice the drops, plus the resets and tails, plus how far the speech level is from -19 dBFS.
  • Transmit score: half the distance of the speech level from -18 dBFS, plus three times the clipping percentage.

Before each change, the balancer waits for a quiet channel: five seconds with no audio and no transmission, up to a limit of two minutes. If the channel stays busy, the run stops. The live rounds also change only one setting at a time, and undo a change that made the score worse by more than 0.5.

The automatic mode is limited to these settings:

  • Receive: rx_gain_db, rx_hpf, rx_agc, rx_gate, jitter_ms, and the app's own buffer where an app is used.
  • Transmit: tx_gain_db and tx_buffer_ms.

3.4Where the live changes come from

The live rounds use the same rules as the page's Audio check. The check measures a few minutes of real use (it judges levels only after 5 seconds of speech) and returns a list of suggestions sorted by tier: tier 0 is audio that is lost or distorted, tier 1 is level, tier 2 is noise and filters, and tier 3 is information. At most two suggestions carry an Apply button at once, and the rest are marked "Later". The balancer takes the highest-ranked suggestion that changes a Pi setting (or the app's buffer) and does not change the microphone. Main rules:

Each applied change can be undone from the page. The balancer itself keeps a change only while its score does not get worse (Part 3.2 and 3.3), and its undo values are the settings it read before the change.

3.5Automatic balancing (always on)

Two tick boxes, one for the receive side and one for the transmit side, switch on a standing balancer that runs inside the page. The choice is kept in the browser (nlAutoBal) and restarts when the page opens. The page must be open and logged in, and it asks the browser to keep the screen on while it runs.

  1. On start, it takes the snapshot (Part 3.1) if none is open, so "Restore original settings" in the Tests card can undo everything.
  2. It measures for one minute of real use, then makes at most one change per side, taken from the keys in Part 3.3 only. It first waits for a quiet channel.
  3. The change is "on trial until the next check". At the next check, if the side's score is worse by more than 2 points, the change is put back and that same change is not tried again for 30 minutes. Otherwise it is kept.
  4. A side with less than 5 seconds of speech in the minute is not judged.
  5. When there is nothing left to change, it settles and checks again every 5 minutes (4 minutes of rest plus the 1-minute window).

It does not run, and says why, while the operator is transmitting or testing the microphone, while a tone test or an expanded balance run is going, or while another check is running. It pauses when the Pi reports a load breach (the same limits as Part 5) or when CPU is above 70 % for 30 seconds, and resumes when the Pi settles. Stopping it keeps the changes already made.

Part 4 · The tone test

What the balancer measures with

The tone test sends a known set of tones out through the transmit node and, in RX mode, records what comes back through the receive path. The balancer's gain steps come from those readings.

4.1The signal

  • Tones. By default 150, 300, 500, 1000, 1500, 2000, 2500, 3000 and 3400 Hz. A request may give 1 to 12 tones between 100 and 3800 Hz, each held for 0.5, 1 or 2 seconds, at -10 dBFS.
  • Identification. The test starts and ends with the operator's callsign sent as Morse ("DE" and the callsign, 700 Hz, 20 words a minute). The test refuses to start without a callsign.
  • Length. The whole test must fit within the transmit time limit less 5 seconds, and within 120 seconds.

4.2Before it starts

  1. The node's links must be readable, and the main node must have no links other than node 1921. In TX mode, one extra link is allowed: the tone test link (the operator can connect the main node to a second node for this, and disconnect it afterwards). A tuned connection (for example a digital-mode tune) also blocks the test.
  2. The channel must be quiet: if audio above the activity level was heard within the last 3 seconds, the test waits.
  3. The node must not be transmitting, and the key-up checks (TX path, Part 3) must pass. A test does not use phone tones.

4.3RX mode and TX mode

RX mode records the receive audio twice, as it arrives and after the cleanup stage, while the tones play. It then finds where the return audio starts (three frames at least 12 dB above the noise floor), and for each tone measures its level, its frequency error and its second and third harmonics. The report gives the delay, the noise floor before and after cleanup, the number of dropouts, and the band between the frequencies that stay within 6 dB of the 1000 Hz tone. If nothing returns, the report says the node may not be sending transmitted audio back, so only the transmit levels mean anything.

TX mode only sends the tones. It measures nothing on the Pi, and the operator or a second node listens for the result.

4.4Stopping

A test stops, with a message, if the operator asks, if the transmitter drops out, or if the load guard or the link check trips (Part 5).

Part 5 · The load guard

Stopping a test when the Pi is strained

While a tone test runs, a watch checks the Pi each second. The test stops, with a message, when any of these holds:

CheckLimit
CPU useAbove 90 % for 10 seconds in a row
Free memoryBelow the larger of 40 MB or 10 % of the total
Temperature80 degrees C or more
ThrottlingThe Pi reports it is throttling

The watch also checks the link to the node at intervals. A test stops with a message if the node is no longer linked or ready.

Part 6 · Settings kept on the phone

Microphone and playback settings

Not every audio setting lives on the Pi. The page keeps the operator's microphone and playback choices in the browser of the phone or laptop (local storage, keys nlMic and nlPlay). They are per device, they are not in nodetalker.conf, and the balancer's snapshot does not include them.

GroupDefaultItems
MicrophoneNoise suppression on, high-pass on, leveler on; the rest offAGC, noise suppression, echo cancellation, gain (dB), high-pass, leveler, noise gate (0 off, 1 light, 2 strong), equalizer
PlaybackAll on16-bit stream (otherwise u-law), smoothing, automatic start, spectrum display

The Audio check can suggest a microphone change (gain between -12 and +24 dB, noise suppression, or the noise gate). The page applies it to the phone's own settings, and the balancer never makes that kind of change.

Part 7 · Points for the book

What the balancer and settings show

5.1Change one thing at a time

The balancer's rule is the important one for operators: one setting, one measurement, keep or undo. A tester who changes several settings by hand gets no such check, and the book should say so.

5.2Read the level switch first

An operator who edits the gain and sees no change should check the level switch. The gain only takes effect when it is on.

5.3A run can be left open

A balance run that is not restored or kept leaves its file behind, and blocks the next run. The page offers a restore. The book should tell operators to restore or keep a run before they start another.

5.4Not checked

  • The Audio check's measurements (how the page computes clipping, speech level and spread), which feed the rules in Part 3.4.
  • The app's own buffer, which is changed by the app and not by the server.
  • The exact tone measurement on a running node.
