Part 2 · Repo checks

What check_repo.py enforces

The script compares the changed files with the base branch and fails the pull request on any of these. It prints each problem, or "OK" with the number of files checked.

GroupRule
CodeEvery changed Python file compiles and passes pyflakes. Page script inside a Python file is extracted and parsed with node --check (module scripts as modules). Shell files pass bash -n.
VersionsOne file per tool. The file name and the version inside agree. Three parts for a release, four for a cosmetic build. The pi02w suffix is present or absent as the tool requires. A new version is newer than the previous file. A cosmetic build follows its release and may keep its file name only if the code did not change, only text.
RecordsThe README lists the file. The tool's changelog has an entry and its "Current file" line is right.
Shared codeEach function in shared/confio.py is identical in every tool its USED_BY table lists. The shared look (font and colour lines, welcome and licence text) is present in the eight web tools. The launcher text is identical wherever it is written.
Channelschannels/stable.json may not be edited by a pull request. The other channel files must have the right shape.
AndroidA change under android/ raises the app version and adds a changelog entry.

The checks cannot judge whether a change is correct. They keep the files, versions and copies consistent, so a node can mix versions safely.

Part 4 · The release gate

From main to Stable

  • main is the Testing channel (opt-in on nodes). Stable is the default, and only the promote-stable workflow writes it.
  • The rules are in channels/rules.json: a release becomes stable once 4 newer releases of that tool are on main and it has been there 3 days, or once it has been the newest release for 14 days. Cosmetic builds do not count. A floor sets the lowest version a tool may be promoted at.
  • channels/overrides.json (changed only by pull request) can hold a version back or send a hotfix to Stable at once. The file today holds back versions of wifimon, 44helper, Node Talker and instmon, and hotfixes versions of instmon and pibrary.
  • The workflow runs daily and on every push to main, and retries its push up to three times.
  • On a node, instmon checks each download against its git blob id, so a changed file is refused (instmon part 1 of this series).

The delay is the audit: a bad release has days on Testing to be noticed, and a hold in overrides.json stops it reaching Stable.

Part 6 · Fact-checking

How the summaries were checked against the code

Each of the 26 summaries was read against the source. The methods below found real errors, and each can be repeated.

MethodWhat it catchesExample from this series
Search for the constant or stringA wrong number, name or pathLockout starts at the fifth failure, not the first; each tool has its own cookie name
Load the module and count its tablesCounts that were estimated by eyeThe 44helper step tables: ASL3 has 16 install steps, not 15; Ampersand 7 and 6, not 12
Compare function trees (ast)A shared function that has driftedAll 52 copies of the 13 shared functions match
Hash extracted textA copied block that differsThe launcher is identical in all 11 files
Parse the markup with an HTML parserCounts distorted by script textControl and ARIA counts per page, corrected
Follow a call to its endA claim about a feature that the code does not supportPhone tones are sent by the Dashboard, not by Node Talker; the kerchunk log is kept in the Suite Log file
Read the gate, not the labelA name that sounds like a rulePibrary's "access" and SysMon's "lan" flag only label a client; they refuse nothing
Search the whole repo for what is absentA missing protectionNo sandbox directive in any unit; five tools serve plain HTTP; the pi02w SysMon has no audit
Render and lookLayout faultsA wrong footer label, and pages holding one stray line

6.1Kinds of error found

  • Numbers and names that were right once and drifted (counts, limits, file names).
  • A claim taken from a manual and not checked in code, or the reverse.
  • A feature described from its label, when its code did something narrower.
  • Something real that the first reading missed (connection caps, the shared login file, the custom command mode).

Summaries mark what was not checked. Those lists are the next place to look.

Part 7 · Finding problems

A plan, in order

7.1In the repo

  1. Run python3 ci/check_repo.py --base origin/main. Fix every line it prints.
  2. Run python3 ci/test_ci.py, then the baseline and server tests. A failure in a baseline means the audio changed.
  3. For a page change, run the page and authenticated tests on a runner that has Chromium, or open the page headless and watch the console.
  4. Run pyflakes and node --check on what you touched, and exercise the changed behaviour.
  5. Search for the name you changed in every tool: shared functions and the launcher live in many files, and the full build repeats the pi02w code.

7.2On a node

  1. Look at the Boot tab or run 44helper.py --boot-report --json: clock, power, restarted units.
  2. Look at SysMon's quick tests and port conflicts, and (full build) the audit.
  3. For audio, read Node Talker's health verdict first. It names the layer that lost audio.
  4. Start an instmon Suite Log collection, reproduce the fault, and read the coverage table for silent sources.
  5. Check the tool's own log and the service journal; look for lockouts, refused requests and rollbacks.

7.3Symptom to place

SymptomLook at

8.1Product gaps the tests cannot fix

  • The pi02w SysMon has no security audit. Only the full build does.
  • Five tools serve plain HTTP, and every service runs as root without sandboxing (see the security summary).
  • Memory and timing on a Pi Zero 2 W (the launcher savers, the light-theme filter) were not measured.

8.2Suggested order

First the workflow-only changes (1, 5, 6, 18); then the server and security tests (2, 3, 4), which cover the largest untested surface; then the small additions (7, 8); then 9 to 12 and the rest.
