Chapter 1 · Overview

The suite at a glance

ASL-DVS is a set of five small web tools that run on the same Raspberry Pi as your AllStarLink node. Each tool has its own page in the browser. Together they let you run, check, repair and update the node without typing commands.

1.1What is on the node

The tools sit on top of a working AllStarLink 3 (ASL3) node with DVSwitch. It helps to know the main parts, because the tools check and talk to all of them:

PartWhat it does
Asterisk + app_rptThe ASL3 engine. It runs your node, links to other AllStarLink nodes over IAX2 and handles EchoLink.
Analog_BridgeTurns the node's audio into digital voice and back again. It talks to Asterisk on a private node (1999 by convention).
MMDVM_BridgeConnects Analog_Bridge to the digital networks: DMR directly, and System Fusion, P25, NXDN and D-STAR through their gateways.
GatewaysYSFGateway, P25Gateway, NXDNGateway and ircDDBGateway. Each one connects to that mode's reflectors or talkgroups.
USRP2M17Bridges a second private node (1917 by convention) to an M17 reflector.

Every page has a header with the tool's name and version and a Log Out button. Most pages have a row of tabs under the header; click a tab to switch view. The pictures below show each tool's tabs in order.

1.4Two builds: Pi Zero 2 W and full

The Dashboard and SysMon come in two builds. The other tools have a single build that runs on every Pi.

Pi Zero 2 W build PI02W

For the 512 MB Pi Zero 2 W. This manual is written for it.

  • Dashboard: every tab is kept. It searches the AllStar and EchoLink lists from disk instead of memory, and refreshes less often.
  • SysMon: drops the Firewall, Reg, Net, Zello and Console tabs to save memory.

Full build FULL

For a Pi 3, 4 or 5.

  • Dashboard: the same tabs, and it keeps the lists in memory.
  • SysMon: all 19 tabs. Chapter 6 covers the five extra ones.

Which build am I running? Look at the version in the page header. A Pi Zero 2 W build version ends in -pi02w, for example 6.13.67.11-pi02w. A full build version doesn't, for example 6.13.77.

1.5Logging in

  1. Open the page in a browser: http://<pi-address>:<port>, for example http://192.168.1.50:9999 for SysMon.
  2. Type the Pi's root password and press Log In. There is no user name.
  3. When you're done, press Log Out in the header, especially on a shared computer.
  • The Dashboard and SysMon share one login. Log in to either one and the other opens without asking, in the same browser. A shared login lasts 12 hours from the last time you used either page.
  • instmon, wifimon and 44helper each have their own login.
  • Wrong passwords lock you out for a while. On the Dashboard and SysMon, five wrong passwords within 5 minutes lock that address out of both for 15 minutes. The other tools have similar limits. Wait it out; don't keep guessing.
  • 44helper stays logged in until you log out, press Log out all devices, or the Pi reboots, because its jobs can run for a long time.
CAREFULThe pages use plain HTTP, so your password crosses the network unencrypted. Only open them on your own network or over a VPN or tunnel, never straight from the internet. Chapters 7 and 8 cover safe remote access with 44helper.
TIPIf the login is always refused, set the root password again on the Pi with sudo passwd root. Raspberry Pi OS ships with root locked, so a new Pi needs this once.

1.6Phones and tablets

The pages are laid out for phone, tablet and desktop widths. On a phone, wide tables hide their less important columns, and the tab row wraps onto more lines. Turning a tablet to landscape shows everything.

Leave a page open only while you're using it. Each open page polls its tool for fresh data, and on a Pi Zero 2 W that costs CPU and memory.

The Dashboard and SysMon program paths are links into /usr/local/lib/asl_dvs/ and /usr/local/lib/asl_dvs_sysmon/. The installed file keeps its own name, so the version is always visible on disk.

One process each, started through the launcher

Every service starts its tool through the shared launcher /usr/local/bin/asl_dvs_launch.py:

ExecStart=/usr/bin/python3 /usr/local/bin/asl_dvs_launch.py /usr/local/bin/sysmon.py

The launcher loads the tool as a module so that Python keeps its compiled copy in __pycache__. That roughly halves each tool's memory (SysMon on a Pi Zero 2 W: 54 MB started directly, 26 MB through the launcher). The launcher also turns on three memory savers: python3 -OO, MALLOC_ARENA_MAX=2 and a periodic malloc_trim. Each has an off-switch file in /etc/asl_dvs/ named launch_no_optimize, launch_no_arena_cap or launch_no_trim.

How a page works

  • Each tool is a small Python HTTP server. The page's HTML, CSS and JavaScript are built into the tool's file, so there is nothing else to install and no web server to configure.
  • The page fetches live data from the tool's own /api/... addresses as JSON and redraws its cards.
  • The login checks the password against the root entry in /etc/shadow, and sets a session cookie. Requests that change anything also need a matching CSRF header, so another web page can't act for you.
  • Version numbers come from the VERSION line in each file. The -pi02w suffix is how the installer and instmon recognise the Pi Zero 2 W build.

Checking on a tool from the shell

# is it running, and its last 30 log lines
systemctl status sysmon --no-pager
journalctl -u sysmon -n 30 --no-pager
# is anything listening on its port?
ss -tlnp | grep 9999
# restart all the web tools
sudo systemctl restart sysmon asl_dvs_dashboard instmon wifimon 44helper

2.1Before you start

  • A Raspberry Pi already running AllStarLink 3 with DVSwitch set up.
  • SSH access with sudo, and a root password (sudo passwd root).
  • On a Pi Zero 2 W, some free memory. Check with free -m. The install manual lists services you can turn off if you don't use them.

2.2Install in three steps

  1. Get the files. Download the current files from github.com/kd8pgk/ASL-DVS into one folder on the Pi.
  2. Install instmon first. It can then install and update everything else from the browser. 
    sudo python3 instmon_v2_40_0.py --install
  3. Install the rest with the installer. On a new node it asks for your callsign, node number and a label. 
    sudo bash install_v6_7_0.sh

The installer picks the build for you: the Pi Zero 2 W build on a Pi Zero 2 W, the full build on anything else. If one build is already installed, it keeps that build. When it finishes, it checks that each tool is running and listening on its port.

TIP44helper is optional. Install it the same way, or from instmon's page, when you want its remote-access, installer or Config tools.

wifimon's watchdogs

A new wifimon starts with both watchdogs off: it shows WiFi and voltage, but won't act on them. On your first login it asks whether to turn them on. Add your WiFi networks first.

UNDER THE HOOD

What install and update actually do

--install, per tool

  • Copies the file into place, writes its .service unit, and writes the shared launcher if it is missing.
  • Enables the service so it starts at boot, and starts it.
  • --uninstall stops and removes the service and the program. It removes the launcher only once no other service uses it.

How the installer picks a build

  1. SYSMON_VARIANT / DASH_VARIANT set to pi02w or full, if you set them;
  2. otherwise, the build already installed;
  3. otherwise, pi02w on a Pi Zero 2 W and full on any other Pi.

If no file of the chosen build is found, that tool is skipped with a warning; the other build is never used in its place. The installer looks in its own folder, the current folder, /root, /home/pi, your home folder, /tmp and instmon's library. --non-interactive (or -y) skips every question and takes the identity from AUTO_CALLSIGN, AUTO_NODE and AUTO_LABEL.

The checks on every download

Before instmon saves a file from GitHub, the file must match GitHub's file list. It must also have a version line and the right first line, pass a syntax check, and support --install.

Full Update, step by step

  1. Downloads and checks every new file before anything changes.
  2. Pauses the web tools.
  3. For each tool in turn, saves a copy of the installed file in the library, runs the old --uninstall, and runs the new --install. If the new one fails, it puts the old one back and moves on.
  4. Updates instmon last. A timer reinstalls the old instmon if the new one isn't answering after 90 seconds.
  5. Ends with a summary. New install scripts go only to the Scripts library and are never run for you.

On a Pi Zero 2 W, the build choice decides which build Full Update installs. A tool installed in the other build is listed as SWITCH and replaced. On other Pis the choice is hidden and each tool keeps its build.

Settings that survive an update

Config files in /etc are never touched by an update. SysMon's Hardware tab options (HDMI and video driver off, lower GPU memory) are saved when SysMon is uninstalled during an update and put back on install, if the install follows within 30 minutes.

Chapter 3 · SysMon

SysMon basics and live status

This chapter covers the parts of SysMon you see every time: the header and command bar, then the four status tabs: Overview, Services, Ports and Journal. Open SysMon at http://<pi-address>:9999.

3.1What SysMon is for

Open SysMon when something on the node isn't working, or when you want to be sure everything is. In one place it shows:

  • whether Asterisk, the DVSwitch bridges, the gateways, USRP2M17 and the ASL-DVS tools are running;
  • the Pi's load, memory, temperature and power health, updated every 5 seconds;
  • which programs are listening on which network ports, and whether two of them clash;
  • the system log (journal) of any service, filtered and ready to copy.

The status tabs can also start, stop and restart services. Everything else in SysMon is either read-only or asks before it changes a file.

3.7Common tasks

A service shows red

  1. On the Overview, note the NR: count. A high count means it keeps crashing.
  2. Open the Journal tab, click the service, choose 200 lines and filter on error.
  3. Fix the cause. It is usually a config file, covered on the ASL-DVS, DVSM, STFU and M17 tabs (Chapter 4).
  4. On the Overview, press Reset, then Start. Watch the dot turn green.

Find out what is using a port

  1. Open the Ports tab and press UDP or TCP.
  2. Find the port number. The Process and Known Service columns name the owner.
  3. If it shows [DUP], hover over it for both programs, then stop or reconfigure one of them.

Add a service to the Overview

  1. Services tab, press All, and filter for the service.
  2. Click it, pick a group under Pinned Services (or "New group…") and press Pin.

Send someone a status report

Use Copy on the Overview, the Services list, a Ports table or a journal window, and paste it into your message. Copies are plain text, so they paste cleanly into an email or forum post.

Where the data comes from

  • Services: systemctl show and systemctl list-units. The owner comes from the running process, or from User= in the unit.
  • Ports: ss -tlnpu, with each process's command line from /proc/<pid>/cmdline.
  • Journal: journalctl -u <unit> -n <lines>, between 10 and 2,000 lines.
  • Power: vcgencmd get_throttled. Its bits give under-voltage, frequency cap, throttling and temperature limit, both now and since boot. Without it, SysMon shows the core voltage instead.

Service actions

Every action goes to POST /api/svc. Unit names are checked before anything runs.

  • Simple actions (start, stop, reset-failed, enable, disable, reload, mask, unmask) run the matching systemctl command, with a 15-second limit.
  • Restart runs in the background: systemctl stop, wait up to 15 s; if it is still running, SIGKILL and wait up to 5 s; then systemctl start and wait up to 10 s for it to become active. The result goes to SysMon's own log.
  • Kill sends SIGKILL to the main process. systemd may then restart it, depending on the unit's Restart= setting.
  • Stop All runs systemctl stop on each pinned unit except sysmon.service. Restart All runs systemctl restart on each pinned unit, SysMon included.

The pinned list

The Overview groups come from [services] pinned in /etc/sysmon/sysmon.conf, one line per entry:

__GROUP__:Asterisk Core
asterisk.service | ASL3 Asterisk/app_rpt | /etc/asterisk/rpt.conf | 4569 | udp
# unit | description | config_path | port | proto   ( - for none )

You can edit it as text on the Edit tab (Chapter 5). Pin and Unpin rewrite it for you.

Login and process

  • SysMon runs as root, because it reads every config file and controls services. It refuses to start as any other user.
  • SysMon and the Dashboard keep their logins in one shared file, /run/asl_dvs/auth_session.json (mode 600, locked while written). Both use the cookie asl_dvs_session, so one login covers both pages. A session expires 12 hours after it was last used. Five failures from one address within 5 minutes lock it out of both for 15 minutes. /run is cleared at reboot, so a reboot logs everyone out.
  • The password is checked through PAM, with /etc/shadow as a fallback.
  • The page is built once at start-up and sent compressed. Everything after that is small JSON requests.

UNDER THE HOOD

How the full-build tabs work

Firewall

  • Backend detection order: ufw, firewalld, then nftables or iptables (raw listing only). ufw rules come from ufw status numbered; each row's number is what ufw delete removes.
  • Add runs ufw allow|deny|limit <port>/<proto>, with from <addr> if given. On firewalld, SysMon runs firewall-cmd --add-port both with and without --permanent.
  • Enable reads the SSH port from sshd_config (22 if unset), looks in ufw show added for an allow or limit rule on it, runs ufw allow <port>/tcp if there is none (and stops if that fails), then runs ufw --force enable. Disable runs ufw disable. Endpoint: POST /api/firewall.

Reg

Live state: asterisk -rx "rpt show registrations", part of the background poll (every 30 s), with node numbers matched against the config files. Files: rpt_http_registrations.conf, iax.conf, rpt.conf and Allmon3's allmon3.ini.

Net

The hostname steps run hostnamectl set-hostname and update the 127.0.1.1 line in /etc/hosts, then install and enable avahi-daemon and libnss-mdns, and test the .local name from the node itself. Every command is shown before it runs, and Copy gives it to you for SSH if SysMon isn't running as root.

Zello

Service asl-zello-bridge; settings in /etc/systemd/system/asl-zello-bridge.service.d/override.conf as Environment= lines (USRP_BIND, USRP_HOST, USRP_RXPORT, USRP_TXPORT, gains and the Zello keys). Expected ports: RX 34012, TX 32012, node 1918. Live status parses Keyed: and UnKeyed: lines from the journal.

Console

  • The on/off switch is the file /etc/sysmon/console.enable. It must be a plain file owned by root and not writable by anyone else, or the console stays off. The page writes who switched it on, from where and when. You can also create or remove it from a shell.
  • Opening gives a one-time ticket, valid 60 seconds and tied to your login. The console then runs in a real terminal over a WebSocket, with its home directory in /var/lib/sysmon/console-home.
  • Refused when the request carries proxy headers (Cf-Connecting-Ip, Cf-Ray, X-Forwarded-For and similar), or comes from an address that isn't loopback, link-local or private.
  • The command buttons run fixed commands from an allow-list (/api/console/run). They don't need the console switched on or open. The node number comes from the list of your local nodes.

Safety checks before an install step

  • Masked services. At the top of each install tab (and the Update tab) a card checks whether any service the tab needs is masked (blocked from starting). 44helper clears masks by itself and leaves those services off. You can Turn on each one, or Put the mask back (on purpose) so 44helper leaves it alone. While a mask can't be cleared, the card turns red and the tab's install buttons are locked.
  • Broken packages. Before any step that installs or removes packages, 44helper asks the package system for unfinished or broken packages. If there are any, the step is refused with "NOT RUN" and a pointer to the Update tab's Package recovery steps (Chapter 10).
  • What to do next. When an install step fails, a box opens under it with numbered repair steps. Each one has a button that jumps to the right Update-tab card, and a link brings you back.
  • Repair, then purge. If a purge is refused because packages are broken, it offers to repair them in quiet mode and then run the purge again by itself.

The built-in terminal

A few steps need you to answer questions on screen, for example asl-menu, the USRP2M17 installer and Ampersand's first run. Those cards can open a real terminal in the page, but only:

  • after the terminal has been switched on (from the page with the root password, or by creating /etc/44helper/terminal.enable over SSH);
  • from your local network, never through a tunnel or Cloudflare;
  • with the root password entered again each time you open it;
  • for the one command printed on that card, nothing else.

One terminal at a time. It closes after 10 minutes with no typing, or when you log out.

Jobs

  • A step's Run posts {mode, distro, step_id, command_text} to its tab's /api/<tab>/action. The step must exist in that tab's script list; the command text itself runs through the shell, as root.
  • Package-changing commands (apt, dpkg) run as their own systemd job, not inside 44helper. They keep going if 44helper restarts, and the page re-attaches to them. Package, build and install-script commands have no time limit; anything else stops after 15 minutes unless the step sets a different limit.
  • Before a package command: an install step on a tab runs the masked-service check, which unmasks and disables any masked service the tab needs; then dpkg --audit must come back empty.
  • The page polls /api/action_status?job_key=… about every half second, and keeps retrying if the connection drops.
  • Every POST needs the login cookie and an X-Requested-With header (CSRF protection). Wrong passwords share one 5-try lockout across the login, the terminal and other password prompts.

Port roles

Each reference port has a role. peer-inbound ports (4569, 5198-5199, 1667 and 4568, all UDP) should be open when used. mgmt-LAN ports (5038, 8080, 8989, 9090, 9997 and 9999) and loopback-only ports (31100, 31103, 32008, 34008, 32012, 34012, and the command ports 6073-6075 and 54321) must never be exposed. outbound-only (7844, Cloudflare) never needs an opening. "Exposed" means in the 44NetConnect zone (Pi-hosted), in the router's forwards (router, single address), or the whole subnet (router, routed subnet with masquerade off).

The steps

  1. Firewall prereq: installs and starts firewalld.
    1a. systemd-resolved prereq: installs WireGuard and systemd-resolved, without which the tunnel can fail to start. A reboot is recommended after this, before step 6.
  2. Create the 44NetConnect zone.
  3. Add inbound services and ports: tick what other stations may reach. AllStarLink IAX2 and EchoLink/SvxLink are ticked by default; VOTER/RTCM is optional. Asterisk AMI can be added but is flagged red. Full Tunnel also has fields for your DVSwitch Mobile port and a custom port.     4b (Split): Repair AllowedIPs fixes a config pasted unedited. 4b (Full): optional outbound rules for your digital-voice reflector ports.
  5. Attach wg0 to the zone.
  6. Enable + start the tunnel, then Verify: checks your public address through connect.44net.cloud/myip and Asterisk's AllStar registrations.
CAREFULStarting the tunnel can change how the Pi answers the network. If you are connected over SSH or Cockpit from outside your home network, that session may drop. Do step 6 from home, or on a keyboard and screen.
CAREFULA Full Tunnel config pasted into the Split Tunnel tab unedited is the classic cause of "AllStar works but DVSwitch and M17 don't": every DNS lookup goes into the tunnel. Use step 4b's Repair button, then restart the tunnel.

Other buttons

  • Convert to Split / Full Tunnel: switches an installed tunnel to the other kind, with a preview first.
  • Purge: undoes the tunnel and the zone.

8.5Cloudflare tab

A Cloudflare Tunnel is an outgoing connection from the Pi to Cloudflare. Cloudflare then serves a hostname you choose, such as node.example.com, and passes the traffic down that connection. Nothing is opened on your router.

token method (persistent)

  1. Pre-flight (read-only): is cloudflared already installed, which ASL-DVS pages are running, and how it fits with any WireGuard tunnel.
  2. Install cloudflared from Cloudflare's package repository.
  3. Install the connector service (manual): copy the sudo cloudflared service install eyJ… command from your tunnel in the Cloudflare Zero Trust dashboard, and run it over SSH. It is done by hand on purpose, so your token never lands in 44helper's log.
  4. Verify the connector: service status and recent log. The Zero Trust dashboard should show the connector as Healthy.
  5. Map a Public Hostname and add an Access policy in the Zero Trust dashboard, for example http://localhost:9999 for SysMon.

quick method (test only)

Run cloudflared tunnel --url http://localhost:8989 over SSH. It prints a random *.trycloudflare.com address, needs no account, and stops when you press Ctrl-C.

CAREFULA Cloudflare Tunnel bypasses the firewall. Nothing opens inbound, so 44helper's Ports and Firewall tabs can't see what you have published. Anything you map is reachable by the whole internet, protected only by that page's own login. Always put a Cloudflare Access policy (for example, email one-time codes for your address only) in front of every hostname. Never publish 44helper itself.
NOTECloudflare works with no WireGuard tunnel or with a Split Tunnel. Under a Full Tunnel it still works, but its connection rides the 44Net tunnel and drops whenever the tunnel does.

How the installers are built

  • Each tab's steps live in a Python table (_ASL3_SCRIPTS, _DVSWITCH_SCRIPTS, _SVXLINK_SCRIPTS, _M17_SCRIPTS, _AMP_SCRIPTS, _CF_SCRIPTS), keyed by install or purge and then by script. The page fetches them from /api/<tab>/script.

How updates and optimizations are applied

Quiet mode

  • The state is kept in /etc/44helper/44helper_quiet_state.json: what was stopped, and why. That is how Turn off restarts exactly that set, even after a 44helper restart.
  • Matching uses unit patterns per tier (for example *sysmon*.service). Anything matching the never-touch list (*44helper*, *wifimon*, ssh*, cockpit*, NetworkManager*, firewalld*, systemd-*, dbus*, wpa_supplicant*, polkit*) is skipped. A running mandb is killed between tiers.
  • Turning on is refused while any dpkg or apt lock is held. Each stop waits up to 150 s.
  • Reboot node schedules systemctl reboot 3 seconds later with systemd-run, so the page can show the reply first.

Update steps

  • Package steps run as systemd jobs. Ticking Run in quiet mode wraps the job in quiet mode, at low CPU and disk priority. The recovery steps run under nice -n 19 ionice -c2 -n7.
  • Step 10 finishes packages whose status letter is U, F, W or t. It does kernel and firmware packages (linux-image, raspi-firmware, initramfs-tools and similar) in a separate last pass, then runs dpkg --configure --pending.
  • Step 11 reinstalls packages flagged R, or with missing list or md5sums files, from /var/cache/apt/archives. It falls back to apt-get download into /tmp/44helper-debs.
  • fail2ban writes /etc/fail2ban/jail.d/44helper-fail2ban.conf with backend = systemd, which is needed once rsyslog is off and /var/log/auth.log no longer exists.

System Optimization

  • noatime: the candidate fstab is checked with findmnt --verify before it is written, then applied with mount -o remount,noatime /.
  • journald: a drop-in at /etc/systemd/journald.conf.d/44helper-sysopt.conf; Revert removes it.
  • Each Revert puts back the state saved the first time that card changed something, not a fixed default. "Nothing to revert yet" means this tab hasn't changed it.

Where the copies live and how restores are written

Library

  • Everything lives under /etc/asl_dvs/instmon_library/config_restore/ (or $INSTMON_LIBRARY_DIR), so instmon's Backup & Export ZIP includes it. Automatic copies go under auto/; each point's ID is YYYY-MM-DD_HHMMSS_name.
  • Files per system: ASL3: rpt.conf, iax.conf, extensions.conf, modules.conf, manager.conf, allmon3.ini; optional echolink.conf, rpt_http_registrations.conf, savenode.conf, simpleusb.conf and the /etc/asterisk/custom/ copies.   • A system counts as installed when its marker exists: rpt.conf, the MMDVM_Bridge or Analog_Bridge program, /opt/USRP2M17, or phone.json.

Writing a restore

  • Each file is written through a .44htmp temporary file, created mode 600 and with O_NOFOLLOW, then given the saved owner and mode and swapped into place. Identical files are left alone ("unchanged"). Files whose folder no longer exists are "skipped".
  • A sudoers file must pass visudo -c before it is put in place.
  • Blocks managed by another tool, between ; >>> … managed by … >>> and ; <<< … <<< (such as the Dashboard's Phone block), are recognised when a preset is applied.

Identity scan

  • Fields come from 44helper.conf, rpt.conf, iax.conf, rpt_http_registrations.conf, manager.conf, echolink.conf, the DVSwitch ini files, var.txt, /etc/ircddbgateway and phone.json. In ini files a ; is part of the value; in Asterisk files it starts a comment.
  • Callsigns are compared without a -L/-R suffix. DMR IDs are compared on their first 7 digits for the "same everywhere" band. Only node numbers of 4 digits or more are masked.
  • Reveal uses the same root-password check and lockout as the login. Values are never written to the log.

Reinstall job

Runs as its own systemd unit, asl-dvs-reinstall, so it survives 44helper restarting itself. Its state and log are in config_restore/reinstall_job.json and reinstall.log. It uses a 90-second health guard while the tools come back up.

How the Dashboard drives the node

  • Settings: /etc/asl_dvs/asl_dvs.conf (identity, favorites, visible tabs, DMR networks). Phone: /etc/asl_dvs/phone.json and the dvs_phone_*.conf files it writes.
  • Polling: /api/status every 5 s when idle and every 1 s while a tune is in progress, with an ETag, so unchanged state costs almost nothing. On the Pi Zero 2 W build the AllStar and EchoLink lists are searched on disk rather than held in memory.
  • Tuning: through DVSwitch's dvswitch.sh (mode and tune commands) and Asterisk's AMI on 127.0.0.1:5038 (link and unlink). A tune counts as done when Analog_Bridge's /tmp/ABInfo_*.json confirms it.
  • Changing tab: drops the links except the needed bridge node, sends a talkgroup disconnect, switches the DVSwitch mode, starts or stops the mode's gateway service (YSF, P25, NXDN, ircDDBGateway), and links the bridge node (1999, or 1917 for M17).
  • M17: writes /opt/USRP2M17/USRP2M17.ini in full on every connect and disconnect, and restarts usrp2m17. From 9.3.71.11 (full build 9.3.74) it listens on UDP 17010 (it was 32010, which clashed with P25).
  • Phone calls are placed with AMI Originate into rpt(<node>,Pv). Radio *61 requests arrive through /run/asl_dvs_tones/req and are dialed within about 2 seconds.
  • Service: asl_dvs_dashboard, with Restart=always and WatchdogSec=30, so it is restarted if it stops answering. That is why the separate Watchdog script isn't needed.
  • The login is shared with SysMon (Chapter 3).

UNDER THE HOOD

instmon's files and jobs

  • Program: /usr/local/bin/instmon.py, service instmon, port 8990. Its own login: cookie instmon_session, 12 hours, kept in memory, so restarting instmon logs everyone out and the page reloads to the login screen.
  • Library: /etc/asl_dvs/instmon_library/ ($INSTMON_LIBRARY_DIR), one folder per category: dashboard, sysmon, wifimon, 44helper, watchdog, instmon, scripts, config. 44helper adds config/wg0.conf and config_restore/.
  • Install runs the file's own --install; Uninstall runs --uninstall. A tool is only offered for install if its file supports --install (and --uninstall) and passes the download checks in Chapter 2.
  • Version comes from the file's VERSION, APP_VERSION or SCRIPT_VERSION line, or, for .sh scripts, the title line # name.sh vX.Y (date).
  • Router link: reads the default route from /proc/net/route, and probes the gateway on http:80, then https:443, with a 1.5-second limit, cached for 30 seconds. It is only offered when your browser is on that same network.
  • USB import: a drive not already mounted is mounted ro,nosuid,nodev,noexec (plus noload on ext3/ext4, so a journal is never replayed) under /mnt/instmon-usbimport/<drive> for each request and unmounted after (FAT, exFAT, ext2/3/4, NTFS with ntfs3 or ntfs-3g). Paths that leave the drive, symlinks and hidden entries are refused, at most 500 entries per folder. Endpoints /api/usbimport/drives, /browse and /import.
  • Disk jobs: dd or ddrescue, openssl enc with PBKDF2 for encryption, resize2fs and parted for Shrink to fit, and fsfreeze for Freeze. Throttled copies run as a shell pipeline that won't survive an instmon restart.

wifimon and wifi_menu.sh

wifimon keeps a WiFi node connected, and shuts it down cleanly before low voltage or a lost network can corrupt the SD card. Its page manages your WiFi networks, a travel hotspot and its own watchdogs. Open it at http://<pi-address>:8991. wifi_menu.sh is a text menu for the same WiFi jobs over SSH.

14.1Status

  • The network you are on, a signal meter from −90 to −30 dBm, the IP address, and whether the internet answers.
  • Warnings with one-click fixes: Power save is on (it can cause dropouts; turn it off for this network or all of them) and No WiFi country code (it can keep a Pi's WiFi off or limited).

How wifimon works

  • Files: program /usr/local/bin/wifimon.py, service wifimon, port 8991. Settings and the reconnect list are in /etc/wifimon/wifimon.conf. NetworkManager's own profiles are in /etc/NetworkManager/system-connections. Shutdown state, which SysMon and the Dashboard read, is in /run/wifimon/shutdown_state.json. Reports are in /var/log/wifimon; the newest 10 are kept, each up to 256 KB.
  • WiFi: everything goes through NetworkManager (nmcli). wifimon gives NetworkManager a 30-second head start to reconnect by itself, counts 3 failed checks as "lost", and treats a link with no traffic for 60 s as stuck. It reorders NetworkManager's join order to match the reconnect list.
  • Undo: a risky change is recorded as pending, with a 60-second deadline (120 for options). The page checks in from the new connection to keep it; otherwise the change is undone. A 180-second grace period follows each change.
  • Voltage: sampled through the Pi firmware. Snapshots are taken every 10 s, or every 5 s while voltage is low; the last 20 go into a shutdown report.
  • Login: its own, with the root password, checked through PAM. Sessions last 12 hours. The page polls status every 5 seconds.
  • Setup from the shell: sudo python3 /usr/local/bin/wifimon.py --setup-wifi adds or imports networks. wifi_menu.sh uses nmcli only and doesn't touch wifimon's reconnect list.

15.3No audio, or audio one way only, on digital modes

  1. SysMon Overview: Asterisk, analog_bridge and mmdvm_bridge must all be green.
  2. Dashboard: check the indicator shows the talkgroup or reflector you expect, and that you are on that mode's tab.
  3. SysMon ASL-DVS tab: node 1999's RX and TX ports in rpt.conf must be Analog_Bridge's pair the other way round.
  4. SysMon Ports, and 44helper Config, Port check: no [DUP] and no clash. A known one: M17's old LocalPort 32010 clashes with P25. The Dashboard uses 17010 from 9.3.71.11 (Pi02w) and 9.3.74 (full).
  5. DMR only: SysMon ASL-DVS, check MMDVM_Bridge.ini has a real DMR ID and the network enabled, and STFU (if you use it) has its hotspot password.
  6. On a Split Tunnel: AllStar working while DVSwitch and M17 fail usually means an unedited AllowedIPs. Use 44helper Split Tunnel, step 4b (Chapter 8).

15.4Other nodes can't link to me

  1. SysMon ASL-DVS: rpt_http_registrations.conf (or iax.conf register lines) has your node and a password. On the full build, the Reg tab shows the live registration.
  2. 44helper Ports: IAX2 4569/udp must not say needed-but-not-open.
  3. Behind a home router with no tunnel, the router must forward UDP 4569 to the Pi. With a 44Net tunnel, the 44NetConnect zone must allow iax2 (Chapter 7, Firewall).
  4. Two nodes behind one router need different IAX ports: 44helper Nodes tab (Chapter 8).

15.6The Pi is slow or runs out of memory

  1. free -m. A Pi Zero 2 W has about 415 MB usable, and zram swap is normal.
  2. Check every tool runs through the launcher: ps ax | grep asl_dvs_launch should list each one. A tool started as plain python3 tool.py uses about twice the memory, so run its --install again.
  3. Close pages you aren't using. Each open page polls its tool, and Cockpit's page costs about 27 MB while open.
  4. SysMon Hardware: turn off the video driver and lower GPU memory (Chapter 5).
  5. Turn off services you don't use, such as PackageKit, P25Gateway or Allmon3. The Pi Zero 2 W install manual lists them.

15.7The node switched itself off

  1. wifimon, Activity log, Shutdown reports: the newest report says which watchdog fired.
  2. Low voltage: improve the supply and cable. SysMon's Pwr field shows WARN or ⚡ UV when it happens.
  3. No connection: check the reconnect list has every network the node might use, and lengthen "Shut down after no connection" if the WiFi is often slow to come back.
  4. Report says "stop that wasn't clean": the power was cut or the Pi crashed. Check the SD card (Chapter 5).

15.8An install or update keeps failing

  1. Read the "NOT RUN" reason on the step. Masked services: use the card at the top of the tab. Broken packages: use the "What to do next" buttons.
  2. 44helper Update: run "Is apt still running?", then Package recovery 1, 2 and 3, then 1 again. Don't reboot while recovery 1 lists problems.
  3. Run the failed step again. If it still fails, Purge on that tab (with Repair, then purge if offered), read "Still left behind", and install again.

15.9I lost remote access

  • After starting a tunnel: on the home network, or with a keyboard and screen, use the tunnel tab's Purge, or sudo systemctl disable --now wg-quick@wg0.
  • After a firewall change: a runtime-only test goes away with sudo firewall-cmd --reload or a reboot. On the full build, if ufw was turned on with no SSH rule: sudo ufw allow 22/tcp from a local console, or sudo ufw disable.
  • Banned by fail2ban: the web pages still work. In 44helper, Update, Custom: fail2ban-client set sshd unbanip <your-ip>. Bans expire after 10 minutes anyway.
  • Cloudflare hostname not answering: 44helper Cloudflare, Verify the connector, and check the Zero Trust dashboard shows it Healthy.

15.10Phone calls fail

  1. Dashboard Phone tab open? The phone node only links while it is.
  2. SysMon Phone tab, Health checks: fix every FAIL. Autopatch modules: both features should be READY.
  3. SysMon Phone, Router test: Going out, then Call audio during a Test call, then Coming in.
  4. Dashboard Phone, Report: copy it for anyone helping you. The Phone dialplan guide in docs/ has the full call flows.

15.11The SD card

  • SysMon SD Card: READ-ONLY root, kernel storage errors, or fsck errors mean the card is failing. Image or clone it now (instmon, Chapter 13) and replace it.
  • To restore onto a new card: instmon Restore writes a backup image to a card in a USB adapter. Swap it in and boot.
  • To reduce wear: 44helper System Optimization (Chapter 10).

The launcher and memory savers

Every tool's service starts it through /usr/local/bin/asl_dvs_launch.py, which loads the tool as a module so Python keeps the compiled copy in __pycache__:

Launcher version 2 adds three more savers, each with an off switch:

SaverWhat it doesOff switch
python3 -OODrops built-in help text from the loaded code./etc/asl_dvs/launch_no_optimize
MALLOC_ARENA_MAX=2At most 2 memory pools instead of up to 8 per CPU core./etc/asl_dvs/launch_no_arena_cap

# turn one off for every tool, then restart them

# delete the file and restart to turn it back on

With -OO, the first start after an update compiles everything once more, so measure memory after the next restart. Each tool writes the launcher when it installs, and removes it on uninstall once no service uses it. The launcher's text is identical in every tool.
