The Log Collection System

instmon keeps two logs. Its activity log is the short list of what instmon has just done. The Suite Log is a timed collection, started by hand, that gathers journal lines, file lines, kernel lines and health snapshots from the whole suite into one file, with secrets hidden. This summary covers both, the sources, the limits, the redaction, and how the collection starts, stops and is read.

The activity log is what the Log card on the page shows. It is a short working record. The Suite Log is for after-the-fact questions: what happened across several tools, in a time window.

Part 2 · The sources

Where the Suite Log reads from

2.1Journal units

The collector follows the systemd journal for a list of units: the Node Talker, Node Listen, Node Recorder, Pibrary, wifimon, instmon, the Dashboard, SysMon, 44helper and its netready unit, the Zello bridge, the radio services (the analog and MMDVM bridges, Asterisk, the SVXLink USRP service, the STFU service, the M17 service), Allmon3, the WireGuard unit, and the Amp services. Units named with a pattern (for example asl_dvs_* and wg-quick@*) are matched when they run.

The journal is read with journalctl -f from the moment of start, so only new lines are collected. When the unit list changes, the reader is restarted with the new list.

2.2Kernel messages

A second journal reader follows the kernel log (journalctl -k). Only lines that match a fixed set of patterns are kept: Wi-Fi chip and interface messages, MMC, USB, under-voltage and throttling, thermal, out-of-memory, firmware, I/O errors, ext4 filesystem messages and resets. The kernel lines carry a level, so the urgent ones are never dropped by the rate limit (Part 5).

2.3Log files

Files are read by tail: a new file is read from its last 50 lines, then followed. The list covers Asterisk's full and messages logs, the MMDVM, USRP, DVSwitch and ircDDB gateway logs, the wifimon logs, the SVXLink log, the instmon full-update job log, and the Pibrary logs found on any mounted drive.

2.4Wi-Fi state and snapshots

  • Wi-Fi. The link state file /run/asl_dvs/wifi_link.json is sampled and written as rows.
  • Snapshots. Every 10 minutes the collector writes a snapshot row with the load averages and the memory and swap figures from /proc.
Part 3 · Rows, levels and limits

What each row looks like and what limits it

3.1A row

Each row is one line of JSON with a time in milliseconds (t), a source (src, for example journal:nodecontrol or file:…), a level (lvl: info, warn or err, from the journal priority for journal lines), a kind (kind: for example log, mark, drop, snap, or a kernel-critical kind), a message, and optional structured data. Lines are cut to 2,000 characters, and control characters are removed.

3.2Repeats are collapsed

When the same message arrives again from the same source within 60 seconds, it is counted, not written again. When the run ends, the count is written as one row. The comparison ignores the timestamp at the start of a line, so the same message with a new time still counts as a repeat.

3.3Rate limit per source

RuleValue
Bytes per source per minute98,304 (96 KB)
Lines over the budgetDropped and counted. A warning row records how many were dropped in the minute.
Warnings and errorsNever dropped by the rate limit (urgent).

The total dropped is kept in the collection's counters.

3.4Query limits

A query returns at most 300 rows by default, newest first, and at most 5,000 rows in any case. A query can filter by time window, source, level, kind and text.

Part 4 · Starting, stopping and resuming

The collection's life

  1. Start. The Start button asks for a number of hours, from 0 to 168 (default 12). Zero means it runs until stopped. A random salt is made for this session and written to the flag file. The start is logged in the file as a mark row, with a header that records the settings.
  2. Collect. The readers run as threads: the unit journal reader, the kernel reader, the file reader, the Wi-Fi reader, the memory guard and the snapshot writer.
  3. Stop. Stop kills the reader processes, writes any repeats still held, writes a stop mark with the reason and the counts, and removes the flag file. The salt is cleared.
  4. Automatic stops. The collection stops by itself when its time is up, or when free memory drops below 60 MB (61,440 KB). The reason is written in the stop mark.
  5. Resume. If instmon restarts while the flag file exists, the collection starts again, with its end time read from the saved "until" file.

4.1The flag file

The flag file /run/asl_dvs/suitelog.on holds the salt. It lives in /run, so it is gone after a reboot, and the collection does not resume after one. Stopping removes it.

Part 5 · Redaction

Hiding secrets and tagging addresses

Every row is redacted before it is written, when a salt is set. The same function is used by Node Talker, so both tools' rows are treated the same way.

WhatWhat is written instead
Bearer tokensBearer [hidden]
Passwords, passphrases, secrets, tokens, API keys, auth and cookie values (after a word and a separator)[hidden] in place of the value
SSIDs (after the word ssid)A tag such as ssid: followed by four hex characters
MAC addressesA mac: tag with four hex characters
IPv4 and IPv6 addresses, including LAN addresses (all except loopback and unspecified)An ip: tag with four hex characters
Loopback and unspecified addressesKept as they are

Each tag is the first four hex characters of a SHA-256 hash of the salt and the value, in lower case. The salt is random for each collection. So the same SSID or address always gets the same tag within one collection, which keeps the rows linkable, but a tag cannot be reversed to the value, and it is not the same across collections.

The rows written by a collection are redacted, but the file is only as safe as its readers. The book should say that the collection is meant for sharing with a helper, after a check of its contents.

5.1Rows that are not redacted

The kernel-critical rows (kinds beginning kc) are kept as they are when the log is cleared, so they survive a clear, and they are not redacted again. They are kept on purpose (Part 6).

Part 6 · Reading, clearing and downloading

The viewer and its controls

  • Query. The viewer filters rows by time window, source, level, kind and text (Part 3.4).
  • Sources. The list of sources that have rows, with their counts and last times, can be refreshed by the operator (force).
  • Coverage. A coverage report lists each expected unit and file, and whether it has produced rows. A unit that is not running is shown as such. A collection that has run for at least 10 minutes is judged on that basis.
  • Download. The whole file, the old rotated copy included, downloads as suitelog-<time>.jsonl. A view can also be downloaded as text or as JSON lines.
  • Clear. Clear removes the file and its old copy, and keeps only the kernel-critical rows. The counters are reset.

6.1Rotation

When the file reaches 10 MB, it is moved to a name ending in .1, replacing any older copy. The two files together are the collection. Rows are read from the old copy first, then the new one.

Part 7 · The activity log

instmon's own short log

Every message instmon logs goes into an in-memory ring of 500 lines, with an increasing id. The Log card asks for lines after the last id it has seen, so it gets only new lines. The ring is not written to disk, so it starts empty after a restart. Control characters are replaced with spaces.

Because it is not on disk, the activity log is not a record. For a record of a failed install or update, the Suite Log, the Full Update's job log, or the tool's own journal is the place to look.

Part 8 · Points for the book

What the log system shows

8.1Logs are kept in /run

The Suite Log and its flag live in /run, which is cleared at each reboot. A reboot therefore ends a collection and removes its file. The book should say so, and tell operators to download a collection before a reboot.

8.2Limits protect the Pi

The rate limit, the memory guard and the 10 MB rotation keep a collection from filling the small SD card or starving the node. The book can describe them as its safety rules.

8.3Redaction is useful, not a guarantee

The redaction hides the common secret forms and tags addresses. It does not know about every secret a log line could carry. The book should advise checking a collection before it leaves the node.

8.4Not checked

  • The viewer page's behaviour in a browser (its query and coverage views were read for their routes).
  • The full coverage logic for each unit, and the exact snapshot fields.
  • The redaction patterns in a live log with real secrets.
  • The resume-after-restart path, which was read by name.
